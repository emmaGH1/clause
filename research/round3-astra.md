## What the CLI can actually establish

- **Free-account answer remains open.** The event offers 10,000 credits. The Exploration guide requires sign-in, credits and a Test Manager project. It names HyperExecute as the default host and documents local orchestration with local Chrome. It does not specify a paid tier for local Exploration or explicitly grant hackathon accounts remote capacity. Requirements for remote test suites and physical devices are documented separately. Local Chrome removes the HyperExecute scheduling dependency. Project permissions, API access and credit consumption still matter. Case-creation permission matters for generated tests even when mapping works. [Event offer](https://www.kaneclihack.sh/) · [Exploration prerequisites](https://www.testmuai.com/docs/kane-cli-exploration) · [Remote suites](https://github.com/LambdaTest/kane-cli/blob/main/docs/user-guide/remote-execution.md) · [Device plans](https://github.com/LambdaTest/kane-cli/blob/main/docs/user-guide/mobile/overview.md)
- **First-hour access test for every Exploration proposal.** Record version, identity and balance. In a fresh project on an owned public preview, try the command below. Check the actual session, stop reason, visited screens and ending balance. Remote agent-mode exit zero means queued. If remote launch is refused or never starts, end any active session and retry locally with the same limits and local Chrome. A useful pass is a trace of a real action the coding agent can consume. A screenshot of the native map alone leaves the integration unproved. Local orchestration belongs on the Linux worker. Vercel can serve the Next.js result. [CLI execution and exit codes](https://github.com/LambdaTest/kane-cli/blob/main/docs/user-guide/exploration.md)

```bash
kane-cli explore run --project "$PROJECT_ID" --url "$PREVIEW_URL" \
  --policy read_only --no-context --max-parallel 1 --max-leases 3 --agent
```

- **Three different kinds of evidence matter.** Exploration's read-only policy bounds actions. Finding rechecks record what happened on another attempt. Evidence policies judge metrics in a sealed test run or merged pack. No documented switch makes a map prove an arbitrary claim such as “customers can find refunds.” Put the business observation in a real assertion, then use a blocking policy for failed tests, broken tests and tests without checks. Require the intended case to exist before accepting its verdict. New explorations can disable design jobs with `--no-context`. Otherwise those jobs have their own credit spend, and designed tests still need executing. ## Cross-examination of Opus's three

**A · Wild Bugs. Pass unless a maintainer and a consequential defect are already in hand.** The official example is sobering. Six runs on a public demo store yielded a map, a sign-in barrier and twenty high-severity findings *to review*. A recurring console error can be perfectly reproducible while the shopper completes the task. My triage question is “What did the person try, what visible result did they lose, and can we show it twice?” A clean console after a patch answers a different question. Read-only mode can itself block a necessary request. Record that as a limit of the observation. [TestMu's worked example](https://www.testmuai.com/docs/kane-cli-exploration)

Opus's proposed before/after chain crosses environments. A project keeps one exploration URL. A focused run starts at a known screen. The docs do not promise cross-deployment identity for a finding or that focus forces its former action. A credible version uses an authorized OSS deployment at a stable URL, pins each revision, and runs the same user-visible assertion against both. That is feasible for one already-triaged functional issue. Finding the issue, bringing up a stranger's stack, confirming its impact, patching and producing an acceptable upstream contribution in 2.5 days has too many independent dependencies. The unscripted discovery is distinctive. Everything after it looks like the organizer's suggested PR bot. A local patch with evidence is within the builder's control. Upstream acceptance runs on someone else's clock. [CLI map and focus semantics](https://github.com/LambdaTest/kane-cli/blob/main/docs/user-guide/exploration.md) · [Organizer ideas](https://www.kaneclihack.sh/)

**B · Lost & Found. Best of Opus's three after narrowing the claim.** Start from home with a believable user intention and withhold the feature name and path. “Kane reached this state in these actions” is credible. A missed target means *unseen within this budget and policy*. Read-only controls, authentication, queue failure or the lease cap can explain the miss. A second run in the same project inherits the map and can read annotations, so a faster second attempt is weak evidence of a navigation improvement. Use fresh projects, a frozen URL/version per comparison, identical budgets and an observable destination. Show the first wrong turn, give it to the coding agent, and capture the next independent attempt. The builder can ship that one task in the window. A human discoverability score would need human observations. The nearest collisions are Signed Off on spec coverage and GuardianKane on gating. The valuable output here is the visitor's actual route. [Exploration memory and budgets](https://www.testmuai.com/docs/kane-cli-exploration) · [Landscape review](/data/home/.t3/projects/kane-hackathon/research/terra-landscape.md)

**C · Parity. Strong customer promise, weakest proof.** Two explorations need two projects. A redesigned menu can add a screen while preserving an outcome. Conversely, both maps can end at “Confirmation” while the new form sends the wrong payload. Neither graph similarity nor a sealed pass-rate verdict settles that. Select one owner-authorized flow, use the old app to discover its inputs and expected result, then assert the same observable outcome on the rebuilt route. This could ship as a migration of one calculator with three input/output examples. The app-wide promise, content migration and semantic matching cannot credibly ship together here. C also needs an owner with an old site worth replacing. Without one, the builder supplies both the migration problem and the acceptance criteria. [One URL per project](https://www.testmuai.com/docs/kane-cli-exploration) · [Available policy mechanisms](https://github.com/LambdaTest/kane-cli/blob/main/docs/user-guide/policies.md)

## Final ballot

Scores are estimates in playbook order. **Sponsor** measures whether removing Kane removes the promise. **Both halves** measures whether the same action delivers user and sponsor value. **Gate** covers event eligibility and the riskiest sponsor call. **Real** rewards an identifiable, usable specimen. **Buildable** asks whether the journey could work by halfway. All three get only one gate point until a real account completes the call. Both new proposals are agent-originated.

### 1. Contact Sheet · a working recipe for a look

**When a designer drops in a photo, they get a contact sheet of treatments they can reproduce in miniPaint, and TestMu gets Kane operating a real creative application and certifying which recipes survive replay.**

Run an owned copy of the MIT-licensed editor, preloaded with the photo. Give Kane a visual brief such as “make three poster treatments” and freedom to choose effects and settings. Capture the canvas after each committed effect and retain the action trace. The coding agent turns one trace into an editable recipe, then asks Kane to apply it in a fresh document. The assertion compares exported pixels of the same input at a fixed size and tolerance, including a check that the output materially changed. A sealed verdict admits that recipe to the sheet. The designer can choose it for a second photo. That second output demonstrates reuse, while the same-input comparison supports reproducibility. The product needs no upstream changes and still has a payoff when every effect works correctly. [miniPaint source and examples](https://github.com/viliusle/miniPaint) · [Evidence policies](https://github.com/LambdaTest/kane-cli/blob/main/docs/user-guide/policies.md)

**Biggest risk and hour 1.** Canvas dialogs, pixel capture and menu parameters may defeat reliable replay. Start with one public-domain image and one unscripted effect, using Kane's ordinary browser session plus a policy-judged replay. Exploration is optional for this entry. Require an actual exported image, a reconstructible setting and a genuine verdict on the replay. Change the expected image and require the check to fail. If this needs a hand-authored effect sequence or the worker must implement the filter itself, drop the idea. If it works, ship one editor and three swatches. The judge's proof frame is the source, chosen treatment, recipe and fresh replay in one view.

### 2. The Other Reading · a second route through a branching story

**When a reading-group host submits a branching story, they get two playable readings that diverge at a specific choice, and TestMu gets Exploration discovering the fork that determines the discussion.**

The host can hand one route to each half of the room, then ask where their readings first diverged. Run Exploration on one permitted published story. The coding agent uses observed choice labels to select two paths with a common prefix and distinct later passages. It sends both candidates back to Kane from fresh reader state. If a saved variable collapses them to the same passage, the agent picks another observed fork. Publish the two playable choice lists beside the exact divergence and the two observed passage excerpts. This is a reading-group activity with no opposing agent, escape condition or story repair. A Twine source graph can list authored links. Browser evidence adds whether both readings are actually playable from a fresh start. Chapbook supplies an existing demo specimen, though its suitability for group discussion is unvalidated. [Chapbook and demo source](https://github.com/klembot/chapbook) · [Exploration flows](https://www.testmuai.com/docs/kane-cli-exploration)

**Biggest risk and hour 1.** A single-page story may collapse into one screen in the map. Try one licensed example without giving Kane any choice labels. Require two distinct *observed* passage texts, the actual common choice point and a clean-state replay of both paths. If the trace cannot distinguish passages, drop it. Hard-coding two branches would remove the reason to use Kane. Limit the build to one story format and one real pair. This ranks above B on a tie because the audience gets to use what Kane found.

### 3. Lost & Found · a witnessed first visit

**When a builder submits one task on a preview, they get a first visitor's route and the point where it succeeded or stalled, and TestMu gets a blind Exploration trace that changes the coding agent's next design decision.**

**Biggest risk and hour 1.** A single explorer can make an idiosyncratic wrong turn, and the builder may already have a perfectly clear interface. Use one existing app the builder controls. Give two fresh projects the same goal, budget and start state. Require the agent to recover the actual route from each and distinguish destination reached, budget exhausted and setup failure. If the traces disagree, show both. If neither gives an actionable observation, decline the design-change claim. A reproducible finding could justify one navigation edit followed by a fresh attempt. The tie-break against B is that its output still needs a builder to interpret the evidence before anyone gets a better experience.
